CLIENT ISSUE
When replacing/uploading the protected PDF of a digital product from the admin panel:
- the upload takes a long time,
- the progress percentage does not reach completion correctly,
- and the admin may eventually show that the file could not be uploaded.

ROOT CAUSES CONFIRMED IN CURRENT CODE
1. `assets/js/admin-digital-products.js` allows a hard-coded 50 MB upload, even when PHP/WordPress has a smaller effective upload limit.
2. Network upload progress is capped at 88%, while server-side protected-page processing restarts from approximately 1%, making the visible progress appear stuck or move backwards.
3. Backend PHP upload errors are mostly reduced to the generic `تعذر رفع الملف.` message.

SOURCE FILES
- wp-content/themes/vava-living-theme-ar-v1/inc/digital-products-commerce-vava.php
- wp-content/themes/vava-living-theme-ar-v1/assets/js/admin-digital-products.js

REQUIRED IMPLEMENTATION
1. Apply:
   VAVA-Client-Fixes-Stage-02-Digital-PDF-Upload/patches/0002-fix-digital-pdf-upload-progress-and-limits.patch
2. PHP/backend:
   - Add one helper that returns the effective protected-PDF upload limit as the smaller of 50 MB and `wp_max_upload_size()`.
   - Validate the uploaded file against that effective limit.
   - Expose `maxUploadBytes` and `maxUploadLabel` through `VAVA_DIGITAL_PRODUCTS_ADMIN`.
   - Preserve the existing protected-storage and PDF-processing architecture.
   - Return meaningful messages for standard PHP upload error codes instead of one generic error.
3. JavaScript/admin UI:
   - Read the effective upload limit from localized config instead of relying on a hard-coded 50 MB check.
   - Reject an oversized PDF before starting the request and display the actual allowed size.
   - Treat the network upload as roughly 0–90%.
   - Map queued/processing progress into roughly 90–100% so the visible percentage never jumps backwards after upload succeeds.
   - Display 100% briefly when the protected file reaches `ready`.
   - Surface useful messages for HTTP 413, interrupted requests, and server-side failures.
4. Keep existing PDF-only validation and all current protected-file permissions/security checks intact.
